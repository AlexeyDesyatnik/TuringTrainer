# Работа человека с ИИ-разработчиком

Этот документ описывает процесс разработки, но не содержит требований к
продукту. Требования находятся в
[`PROJECT_SPEC_v2.md`](PROJECT_SPEC_v2.md).

## 1. Разделение ролей

Человек:

- определяет приоритет и формулирует задачу;
- принимает продуктовые и архитектурные решения;
- проверяет результат в браузере и смысл учебного контента;
- сообщает воспроизводимые баги;
- принимает решение о коммите и публикации.

ИИ-разработчик:

- сначала исследует актуальный репозиторий;
- сопоставляет задачу со спецификацией;
- вносит минимальные согласованные изменения;
- пишет или обновляет тесты;
- запускает доступные автоматические проверки;
- сообщает изменённые файлы, результаты проверок и оставшиеся риски.

## 2. Приоритет источников

1. Текущая явно сформулированная задача человека.
2. `PROJECT_SPEC_v2.md` для требований к продукту.
3. Актуальный код и тесты для фактически реализованных контрактов.
4. Вспомогательные документы для методического и процессного контекста.

Если источники противоречат друг другу, ИИ должен указать конкретное
противоречие до изменения публичного поведения. Изменение требования сначала
фиксируется в спецификации.

## 3. Размер задачи

Одна рабочая задача должна иметь один проверяемый результат. Ограничение
«один компонент или не более 100 строк» не является обязательным: важнее
целостность изменения и возможность проверить его отдельно.

Большую задачу следует разделить, если её части имеют разные критерии приёмки,
риски или могут быть независимо протестированы.

## 4. Минимальная структура запроса

```markdown
## Задача
[Какое наблюдаемое поведение нужно получить]

## Контекст
- Связанные требования: [раздел спецификации]
- Связанные файлы или экран: [если известны]

## Критерии приёмки
- [Проверяемый результат]
- [Пограничный случай]
- [Необходимая автоматическая или ручная проверка]

## Ограничения
- [Что не менять, только если ограничение действительно необходимо]
```

Не требуется перечислять реализационные шаги, если важен результат, а не
конкретный способ реализации.

## 5. Шаблон сообщения о баге

```markdown
## Баг
[Краткое наблюдаемое проявление]

## Шаги воспроизведения
1. [Шаг]
2. [Шаг]
3. [Шаг]

## Ожидаемое поведение
[Что должно произойти]

## Фактическое поведение
[Что происходит]

## Среда
[Браузер, ширина экрана, задача, режим]
```

По возможности исправление сопровождается тестом, падающим до исправления и
проходящим после него.

## 6. Проверка результата

Минимальный автоматический набор:

```text
npx tsc --noEmit
npm run test
npm run build
```

Команды уточняются по фактическому `package.json`. Утверждение ИИ об успешной
работе не заменяет результаты команд.

Ручная проверка интерфейса:

- пройти затронутый основной сценарий;
- проверить ошибочный и граничный сценарии;
- открыть консоль браузера;
- при изменении раскладки проверить 1280, 768 и 375 px;
- при изменении управления проверить клавиатуру;
- при изменении прогресса перезагрузить страницу.

## 7. Работа с неудачной реализацией

Если несколько исправлений не устраняют проблему:

1. Остановить расширение текущего решения.
2. Зафиксировать минимальный воспроизводимый пример.
3. Отделить установленный факт от предположения о причине.
4. Попросить сначала воспроизвести проблему тестом.
5. Разделить изменение на минимальные независимо проверяемые части.

Пример запроса:

```markdown
Проблема сохраняется после предыдущих изменений.
Сначала воспроизведи её минимальным тестом и объясни установленную причину.
Не меняй остальное поведение. После воспроизведения внеси минимальное
исправление и запусти связанные проверки.
```

## 8. Git

Коммит выполняется после проверки целостного изменения. Не следует привязывать
коммиты к продолжительности сессии или создавать отдельный коммит на каждую
мелкую попытку.

Рекомендуемые префиксы:

- `feat:` — новая возможность;
- `fix:` — исправление дефекта;
- `test:` — изменение только тестов;
- `refactor:` — изменение структуры без нового поведения;
- `content:` — учебные задачи;
- `docs:` — документация;
- `chore:` — инструменты и развёртывание.

Перед коммитом проверяются статус, diff и отсутствие случайных файлов или
секретов. ИИ не создаёт коммит и не отправляет изменения без явной просьбы.

## 9. Процессные антипаттерны

- просить написать весь продукт одним запросом;
- принимать изменение без просмотра diff и проверок;
- указывать ИИ закоммитить каждую промежуточную попытку;
- лечить симптом без воспроизводимого сценария;
- заставлять реализацию следовать устаревшему плану вместо текущего кода;
- добавлять функцию только потому, что её предложил ИИ;
- смешивать изменение требований, рефакторинг и исправление несвязанного бага
  без необходимости.
